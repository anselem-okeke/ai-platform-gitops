# Prometheus Alerting

## Purpose

This document is the **reproducible implementation and operations guide** for Prometheus alerting in the AI Platform.

The current alerting implementation is centered on the security-critical Sigstore Policy Controller path.

The alerting chain is:

```text
Policy Controller metrics
        |
        v
ServiceMonitor
        |
        v
Prometheus
        |
        v
PrometheusRule
        |
        +--> PolicyControllerTargetDown
        +--> PolicyControllerReconcileFailures
        +--> PolicyControllerWebhookCertificateFailures
        |
        v
alert state
```

This guide explains how to:

```text
define PrometheusRule resources
select them correctly
understand alert expressions
choose thresholds
understand `for:` behavior
verify rules are loaded
query alert conditions directly
test safely
troubleshoot missing/failing alerts
respond operationally
```

The current platform has validated:

```text
PrometheusRule resource exists
rule selector mismatch was fixed
required label `release: kps` is present
Policy Controller scrape target = 1
reconciliation metrics exist
```

The platform has **not** empirically forced every alert into `Firing`.

# 3. Why Alerting Is Part of Security

Admission controls can fail operationally even when policy definitions are correct.

Examples:

```text
webhook down
certificate reconciliation failing
controller reconciliation failing
Prometheus no longer scraping the target
```

If these failures are invisible, the platform may discover them only when:

```text
deployments fail
or
security enforcement behaves unexpectedly
```

Alerting reduces that detection gap.

# 8. Alert 1 — PolicyControllerTargetDown

Purpose:

```text
detect that Prometheus can no longer scrape the Policy Controller metrics target
```

Validated expression:

```promql
up{
  namespace="cosign-system",
  service="policy-controller-webhook-metrics"
} == 0
```

Validated duration:

```text
5m
```

Validated severity:

```text
critical
```

---

# 9. Target Down Manifest Snippet

```yaml
- alert: PolicyControllerTargetDown
  expr: |
    up{
      namespace="cosign-system",
      service="policy-controller-webhook-metrics"
    } == 0
  for: 5m

  labels:
    severity: critical

  annotations:
    summary: Policy Controller metrics target is down
```

The exact annotation text can vary.

The key contract is the expression, duration, and severity.

---

# 10. Meaning of `up`

`up` is generated by Prometheus for every scrape target.

Meaning:

```text
1 = last scrape succeeded
0 = last scrape failed
```

Therefore:

```promql
up == 0
```

is a direct signal that Prometheus cannot scrape the endpoint.

---

# 11. Why the Target-Down Alert Uses `for: 5m`

Without `for:`:

```text
single transient scrape failure
    -> immediate alert
```

With:

```yaml
for: 5m
```

the condition must remain true long enough to reduce noise from brief disruptions.

---

# 12. Why Severity Is Critical

The Policy Controller is security-critical admission infrastructure.

If its metrics target is down, possibilities include:

```text
controller unavailable
metrics service broken
Pod unhealthy
network path broken
service selector mismatch
```

Even if admission still works temporarily, observability is lost.

That deserves urgent investigation.


```promql

    policy_controller_reconcile_count{
      success="false"
    }[10m]
  )
) > 5
```

Validated duration:

```text
5m
```

Validated severity:

```text
warning
```

---

# 15. Reconcile Failure Manifest Snippet

```yaml
- alert: PolicyControllerReconcileFailures
  expr: |
    sum(
      increase(
        policy_controller_reconcile_count{
          success="false"
        }[10m]
      )
    ) > 5
  for: 5m

  labels:
    severity: warning

  annotations:
    summary: Policy Controller is reporting repeated reconciliation failures
```

---

# 16. Why `increase()` Is Used

`policy_controller_reconcile_count` is a counter.

A counter is cumulative.

This is wrong for recent-failure alerting:

```promql
policy_controller_reconcile_count{success="false"} > 5
```

because once the counter passes 5, the alert may remain meaningful forever even after recovery.

Correct:

```promql
increase(
  policy_controller_reconcile_count{success="false"}[10m]
)
```

This asks:

```text
how many failures happened recently?
```

---

# 17. Why Aggregate with `sum()`

Multiple reconcilers may emit failure series.

For example:

```text
WebhookCertificates
ClusterImagePolicy
TrustRoot
other internal reconciler names
```

The current alert is intended to detect:

```text
overall sustained Policy Controller reconciliation problems
```

so it sums recent failures.

---

# 18. Why Threshold Is `> 5`

The current threshold is:

```text
more than 5 failures in 10 minutes
```

This allows occasional transient reconciliation errors without paging immediately.

Do not treat this number as universally correct for every cluster.

If platform scale changes, establish a baseline and revisit the threshold.

---

# 19. Why Severity Is Warning

A few reconciliation failures do not necessarily mean admission is unavailable.

The controller may self-recover.

Therefore:

```text
warning
```

is appropriate for sustained but not yet proven availability-critical failure.

---

# 24. Why Any Recent Certificate Failure Matters

Webhook TLS is part of the API server admission path.

A certificate failure can affect:

```text
API server -> webhook TLS
webhook readiness
admission availability
rollouts
GitOps reconciliation
```

Therefore the threshold is:

```text
> 0
```

instead of waiting for many failures.

---

# 25. Why `for: 5m` Is Still Used

A single failure may be transient.

The `for:` duration requires the condition to remain active long enough to reduce one-off noise.

---

# 26. Why Severity Is Critical

Webhook certificate failure can directly threaten admission availability.

That can block:

```text
Pod creation
Deployment rollout
controller reconciliation
GitOps apply operations
```

Hence:

```text
critical
```

# 27. Full Representative PrometheusRule

A compact representation of the validated configuration:

```yaml

kind: PrometheusRule
metadata:
  name: policy-controller
  namespace: monitoring
  labels:
    release: kps

spec:
  groups:
    - name: policy-controller.rules

      rules:
        - alert: PolicyControllerTargetDown
          expr: |
            up{
              namespace="cosign-system",
              service="policy-controller-webhook-metrics"
            } == 0
          for: 5m
          labels:
            severity: critical

        - alert: PolicyControllerReconcileFailures
          expr: |
            sum(
              increase(
                policy_controller_reconcile_count{
                  success="false"
                }[10m]
              )
            ) > 5
          for: 5m
          labels:
            severity: warning

        - alert: PolicyControllerWebhookCertificateFailures
          expr: |
            increase(
              policy_controller_reconcile_count{
                reconciler="WebhookCertificates",
                success="false"
              }[10m]
            ) > 0
          for: 5m
          labels:
            severity: critical
```

This is representative of the validated rules.

Use the committed manifest as the exact source of truth.

# 28. Alert State Lifecycle

Prometheus alerts move through:

```text
Inactive
   |
   v
Pending
   |
   v
Firing
```

---

# 29. Inactive

Condition is false.

Example:

```text
up = 1
```

for the target-down rule.

---

# 30. Pending

The condition is true, but the configured `for:` duration has not completed.

Example:

```text
target down for 2 minutes
for: 5m
```

State:

```text
Pending
```

---

# 31. Firing

The condition has remained true for at least the full `for:` duration.

Example:

```text
target down continuously for >5m
```

State:

```text
Firing
```

---

# 32. Why Alert State Matters During Testing

If a condition is true but the alert is only:

```text
Pending
```

the rule may be working correctly.

Do not mistake:

```text
not yet Firing
```

for:

```text
broken rule
```

# 50. Troubleshooting: TargetDown Never Becomes Pending

Check the raw query:

```promql
up{
  namespace="cosign-system",
  service="policy-controller-webhook-metrics"
}
```

If no series exists instead of `0`, the exact alert semantics may need adjustment.

A missing target and a failed target are not always identical in Prometheus.

---

# 51. Missing Series vs `up == 0`

Important distinction:

```text
target exists but scrape fails
    -> up = 0

target is no longer discovered
    -> up series may disappear
```

Therefore a mature alert design may combine target-disappearance logic with `absent()` if needed.

The current validated rule uses:

```promql
up == 0
```

Do not claim absent-target detection unless added and tested.

---

# 52. Possible Future Hardening with `absent()`

A future rule could consider:

```promql
absent(
  up{
    namespace="cosign-system",
    service="policy-controller-webhook-metrics"
  }
)
```

This would detect a completely missing target.

Do not add it without validating expected behavior in the current Prometheus setup.

---

# 64. Alertmanager Scope

PrometheusRule defines:

```text
when an alert exists
```

Alertmanager defines:

```text
where the alert is sent
```

This document does not claim a complete Alertmanager receiver configuration.

---

# 65. Future Alertmanager Routing

A production design may route:

```text
critical -> pager/on-call
warning -> Slack/email/ticket
```

based on organization policy.

Do not invent routing before it is implemented.

---

# 66. Silences

Silences suppress notifications.

They should not be used to hide unresolved failures permanently.

Document:

```text
reason
owner
duration
incident/change reference
```

for production silences.

---

# 67. Alert Deduplication

Alertmanager groups alerts based on labels.

Stable labels such as:

```text
alertname
severity
namespace
service
```

help deduplicate repeated notifications.

This is an Alertmanager concern, not PrometheusRule evaluation itself.

---

# 68. Recording Rules

The current implementation uses direct alert expressions.

Future high-scale monitoring may use recording rules for expensive queries.

For example:

```text
policy_controller:reconcile_failures_10m
```

Do not introduce them unless query cost/complexity justifies it.
